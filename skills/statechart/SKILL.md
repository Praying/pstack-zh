# Statechart（状态图）

这张图用读图人的语言，展示系统如何在状态之间迁移。这个人，也就是读者，决定行为是否正确。

## 运行

在仓库之外的临时目录里干活。写一份 TLA+ 规约（spec）和它的配置文件。然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript，所以要用能执行 TypeScript 的运行时来跑。`scripts/statechart` 是一个 POSIX shell 脚本，会自动挑一个。在原生 Windows 上，用 Node 22.18 到 22.x，或者 Node 23.6 及以上，运行 `node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts`。

第一次运行会用 mise 安装 TLC 和 Java，需要联网。

## 写规约

- 把读者认可的每条规则写成一个 INVARIANT。规则可以关于一个界面、一个结果、一个存储值，或者一条消息。如果模型里没有对应这条规则的变量，就加上这个变量。永远不要为了让规则成立而弱化它。
- 把 `Next` 写成各个动作的析取，比如 `YouPressPlay \/ YouPressStop`。不这么写，TLC 会把每一步都命名为 `Next`。
- 没有任何步骤离开的状态会违反 `NoDeadlock`，哪怕它是正确的结束状态也一样。当一个 INVARIANT 或 PROPERTY 已经占用了这个名字时，规则写成 `CHECK_DEADLOCK`。往 `Next` 里加一个只在结束状态为真且不改变任何东西的动作，比如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 里给它一个标签。

## 选定这张图

需要判断力的活由你来干：每个状态和箭头上的文字，阶段（phase）和它们的颜色，标题，以及给读者的报告。把你的工作放进一个视图模块（view module），用 `--view` 传给命令。

为了展示读者的语言，视图导出 `state(vars)`。`state()` 返回的值决定图的形态：

- 返回字符串，得到一张扁平的图：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 返回数组，得到父状态：`export const state = (v) => v.main.split(".");`
- 返回对象，每个键对应一个并行区域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

给每个状态贴上读者看得见或在意的标签，比如 "支付中" 或 "租约已持有，写入待处理"。标签里不要出现变量名。在 `vars` 里，TLA+ 序列是键从 1 开始的对象，所以 `v.pc[1]` 就是 `pc[1]`。集合则是数组。

视图还可以导出 `step(action, from, to)`。它拿到 TLC 的动作名，以及这一步前后的值，返回箭头的标签。把每个步骤标签写成用户看到它发生的样子，比如 "你按下播放" 或 "连接失败"。不要写出代码的名字或 TLA+ 动作名。在图里收尾相同的两个动作用同一个标签，这样它们共用一条箭头。

当一个步骤只在某些条件下才能发生时，把条件用方括号写在标签末尾，用读者的语言，比如 `you press play [while the file loads]`。在分区图（regions chart）里，命令会把对其他区域的条件写在箭头上，用那些区域标签的语言，比如 `[when Offline]`。你的方括号会替换掉它，这样一来同一个状态的两条箭头可能长得一样。所以在分区图里，不要为对另一个区域的条件写方括号。当某个任何标签都没展示的值决定一步走向哪里时，在标签里写出结果，比如 "名单读取失败"。

视图还可以导出这些：

- `group(vars)` 返回阶段的名字。每个图状态用所在分组（group）的颜色上色。当一个图状态背后的模型状态分属不同分组时，这个状态不上色。
- `colors` 给每个分组名一个颜色类。
- `title` 是一个字符串，显示在图的顶部。

命令对每个模型状态最多调用一次 `state()` 和 `group()`，对每一步最多调用一次 `step()`。图和报告都用这些答案。所以每个函数只依赖自己的参数。

停留在同一个标签内的步骤，图里不画。当读者必须看到这样的步骤时，把标签拆开。

目标是 20 条箭头左右或更少，因为更满的图不好读。先从 `state()` 返回更粗的标签。行为相同的值给同一个标签，读者不需要的细节就省掉，比如一个进行中的调用，其返回值不改变任何东西。bug 路径（bug path）上的每个状态要保留，每个标记（mark）也要保留。当合并把一个 `breaks` 状态变成 `mayBreak` 时，规则在哪里被违反就被藏起来了。不要合并违反不同规则的两个状态，否则读者看不出哪条规则在哪里被违反。如果图还是太满，就对读者不需要的步骤从 `step()` 返回 `null`，比如每个状态都有的复位，或者其箭头重复了其他箭头所展示内容的步骤。隐藏步骤时遵守这些规则：

- 每个图状态都要能从起始状态沿箭头到达。
- 在模型里有步骤离开的每个图状态，至少保留一条离开它的箭头。
- 一条箭头上的步骤要么全隐藏，要么全不隐藏。只藏一部分，它的条件就变窄了。
- 在交接（hand-off）里，说清图隐藏了哪些步骤。

## 读报告

- 在图里，违反规则的状态带 `breaks` 类。当它背后只有部分模型状态违反该规则时，带 `mayBreak` 类。图例（Legend）写出每个标记对应的规则。当两条规则被违反时，图例把两条写在同一个标记上，所以要在交接里说清哪个状态违反了哪条规则。在分区图里，当包含它的每种区域状态组合都可能违反某条规则时，这个状态得到一个标记。当某个组合可能违反规则而其中没有任何状态带标记时，该组合里的每个状态都得到一个标记。
- TLC 会越过违反规则的状态继续跑，所以图里画出的是 bug 之后的状态。
- 因为 TLC 会越过 bug 继续跑，状态数不设限的模型可能永远跑不完。常量取小一点，或者加一个 CONSTRAINT。
- 用了 VIEW 或 SYMMETRY 时，TLC 把它视为相同的状态算作一个状态，图里也只画这一个状态。箭头可能指向它，而不是这一步真正到达的状态，报告会说明这一点。
- TLC 会检查越过 CONSTRAINT 或 ACTION_CONSTRAINT 界限的每个状态里的规则，但不继续探索这个状态，也不在它里面检查死锁。当某条规则的 TLC 最短路径终结在这类状态时，图里画出这个状态，报告给出这条路径。界限之外的其他状态，图里不画。这种状态里的死锁不会显示出来。对于 ACTION_CONSTRAINT 排除的每一步，TLC 也会检查这一步之后的规则，哪怕它是通过别的途径到达下一个状态也一样。当某条规则的 TLC 最短路径终结于这样的一步时，图里画出这一步。
- 命令按写好的配置文件跑 TLC 检查规则，只用一个工作单元（worker）。某条规则被违反时，命令移除这条规则，再跑一次 TLC，直到没有规则被违反。第一次出现违反之后，每次运行在 100,000 个不同状态处停止，免得大模型永远跑不完。当一次运行到达这个界限或因出错停止时，报告把没有检查的规则列在 "未检查的规则" 下，图里也不给它们打标记。没被检查的规则可能成立，也可能被违反。要检查它，就把被违反的规则从配置文件里移除，或者把模型弄小。这个界限靠加一个模块实现，该模块改变 TLC 变量的顺序，所以对同一条性质，TLC 找到的反例可能与不加界限的那次运行不同。
- `tlc.out` 是 TLC 按写好的配置文件打印的内容。当图里没有画出某条被违反规则的 bug 路径时，`tlc-RULE.out` 是找到它的那次运行里 TLC 打印的内容。当 TLC 重复第一条警告时，单独跑 TLC 会打印两遍，但 `tlc.out` 只显示一遍，因为 TLC 在本命令读取的输出里略去了第二份。这只有在 Java 以 `-XX:+UseParallelGC` 运行时才会发生，否则 TLC 的第一条警告恰恰就是建议加上这个 flag 的那句，它只打印一遍。

## 展示图

把 `chart.mmd` 以 `mermaid` 代码块的形式展示给用户。图的配额是 500 个状态，由 TLC 按写好的配置文件计数。超过这个数，图里只画通往被违反规则的路径，而当没有规则被违反时，命令不写 `chart.mmd`。每条规则仍然会被检查，报告给出状态数和每条 bug 路径。想看整张图，就把模型弄小。

用 Pele 渲染图。当用户要一张图片，或者图太大没法当文本读时，按 `references/render.md` 来做。除非用户要求，不要换别的渲染器。

## 交接

把每张图和它的 Mermaid 文本交给必须做决定的人。每个 bug 加一行：规则名，读者对这条规则说的那句话，以及报告里以编号给出的路径。说清模型省略了什么。给出能重新生成这些文件的命令，配一个新的 `--out` 目录。

当模型描述的是代码时，对照真实代码重放每条 bug 路径，作为测试或现场复现，每个动作走一步。如果 bug 没有发生，先认为模型是错的，直到你能证明它没错。
