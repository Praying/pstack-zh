# TDD Bug Fix（TDD 缺陷修复）

修一个有清晰、低成本测试路径的 bug 时，先让坏掉的行为变成可执行的，再改生产代码。目标是一个聚焦的回归测试，修复前失败，修复后通过。

不切实际时不要硬凑测试。如果可行的测试需要大范围的工装（harness）搭建、脆弱的 mock、缓慢的端到端基础设施、只有生产环境才有的状态、含糊的复现步骤，或者大面积无关的 fixture 改动，就跳过新增测试，改用最接近的有用验证。

## 工作流

1. **搞懂 bug。** 明确预期行为、当前行为、受影响的路径，以及最小的可观察复现。
2. **选最窄的可执行检查。** 优先用该代码路径已经在用的、最贴近的单元、组件、集成或回归测试。如果没有明显可行的测试路径，不要为了走完流程而从零造一个。
3. **先写会失败的测试。** 加一个最小的聚焦测试，要能抓住这个 bug。测试应编码预期行为，而不是照抄当前实现。
4. **修复前先跑新测试。** 确认它因预期的原因失败。如果它通过了，或因无关的原因失败，先改测试或复现，再动实现。
5. **修 bug。** 做最小的生产改动，满足预期行为，同时保住邻近的契约。
6. **重跑回归测试。** 确认测试现在通过。

## 如果失败测试不切实际

改用最接近的可执行回归检查：有针对性的脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或者聚焦的集成检查。

宁可不加新测试，也不加坏测试。坏测试是那种主要测 mock、编码当前实现细节、依赖时序或无关全局状态、为一个小修要搭昂贵基础设施，或者证明修复后会被立刻删掉的测试。

## 护栏

- 不要为了让测试迁就错误的实现而改测试。
- 不要削弱现有断言，除非预期行为确实变了，而且原因清楚。
- 回归测试紧扣这个 bug。避免大面积的 fixture 改动或无关的覆盖率扩张。
- 如果 bug 是偶发的，尽量让测试确定性化，并记录下被钉住的信号。
- 如果 bug 暴露了更广的一类失败，先落地聚焦的回归路径，再考虑补同类覆盖。

## 最终回复

报告证据，不只是结果：

- 点名修复前失败的测试或可执行检查，以及它产生的失败。
- 点名修复后通过的测试运行，以及做过的邻近验证。
- 如果无法出示修复前失败的证据，说明原因，并描述改用的最接近的回归检查。
