### Multi-phase or multi-PR plan（多阶段或多 PR 计划）

**你拥有的是计划，不是代码。计划是一份检查清单（checklist），负责人逐格执行，操作者凭证据审计。** 计划就是交付物。不要实现。

1. 改动只涉及一两个文件、做法又很明显时，跳过计划。说明并停下。
2. 动笔之前按 `playbooks/prototype.md` 用原型定掉悬置问题。只把跑多少次都定不了的产品或偏好决断拿去问操作者。
3. 写出计划文件。开头写清改什么、按落地顺序排列的 PR 编号、以及依赖图。依赖图说清哪些 PR 独立、从主干（trunk）分出、哪些等哪些、每个可能碰哪些文件。然后每个 PR 一节。一个 PR 就是一次改动，带着自己的证据（**sequence-verifiable-units** 原则（principle）技能（skill））。每节用勾选框列：它依赖什么、它编辑哪些文件、它做的那一次改动、你看到的结果、以及它的验证。
4. 光有测试不算充分验证。只有单元、实况、性能三个勾选框全部勾上，PR 才算验证过。每个实况框都用一个具体场景驱动真实界面，并给出通过谓词。性能框要点名指标、探针、先测好的主干基线（baseline）、以及判失败的那个数。改动了交互的 PR 合并前要等操作者审阅。
5. 交回计划路径，然后停。执行从操作者明确放行才开始。

**回复：** 计划路径、PR 编号连同依赖、受审阅把关的 PR 集合、以及没被证明的部分。
