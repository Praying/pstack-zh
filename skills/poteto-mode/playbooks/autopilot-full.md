### Autopilot-full（全自动驾驶）

**你拥有裁定（verdict），永远不拥有 PR。一个负责人把每个 PR 从构建一路带到合并，在你的 swarm 证明了要落地的代码之前什么都不合并，而 swarm 从没写过这些代码。**

一个裁定只覆盖一个 patch，绿的 CI 只覆盖一个 head。第 4 步跑一次完整 swarm，只有大改动才再跑一次。`playbooks/shipping.md` 里的 patch-id 规则可以延续一条通道（lane）的结果，而每个新 head 都要有自己的绿 CI。

1. **操作者的检查关卡（gate）优先。** 授权只覆盖队列里的条目，所以操作者点名为自己的条目、以及队列外的 PR，都停在可合并状态。让你陈述计划的请求不算放行。
2. **每个 PR 生成一名负责人，把他的工作放在接替者找得到的地方。** 为整个程序一次性解析托管平台。默认用 GitHub CLI（`gh`）。`command -v origin` 成功、且 Origin 能解析这个仓库时，所有 PR 操作都用 `origin pr`。否则留在 `gh` 上，并记录这次回退。永远不要求 Graphite（`gt`）。每个负责人都是一个 Cursor 云代理，负责构建、按 `playbooks/opening-a-pr.md` 开出自己的 PR、在真实产物上证明这个改动、按 `playbooks/babysit.md` 盯到绿、并在第 4 步和第 5 步放行后合并。那本手册说要报告一次变基（rebase）的地方，负责人就变基自己的分支，并用 `git push --force-with-lease` 发布出去。

   尽早开出 PR，让 CI 和机器人和工作并行跑。代码只有在去水（slop-strip，即 `cursor-team-kit` 插件（`/deslop`）的 `deslop` 技能（skill））和 `/no-comments` 这两关之后才算就绪，这样完整 swarm 跑的才是成品代码。然后变基到当前主干（trunk）上，在自证之前报告代码就绪的 head，好让验证跑在 patch 真正落地的那个 base 上。之后每个 head 都要报告，自证、CI 和盯 PR 都完成后报告可合并状态。修复轮保持在那个 base 上，除非主干起了冲突、弄红了 CI、或落地了已知的对同一批文件的并发改动，因为每次变基都会重启 CI。在代码就绪的推送之前、以及在需要验证者的后续推送之前，都要在已提交（commit）的 head 上跑仓库里针对所碰路径的检查。

   假设虚拟机会死。开工后尽快推送一次，并按 **show-me-your-work** 技能在根代理（agent）的存储里开一条决策轨迹（路径在系统提示词（prompt）里），然后每完成一个单元就推送一次，再开始下一个。谁生成子代理（subagent），就在那个存储里记下它的 id、状态、以及根据它这类代理的历史运行得出的卡死超时，这样父级死了根还能探它。只强推你自己的分支，`--force-with-lease` 钉在你最后一次推送或接手的那个 SHA 上；出现任何不是你做的推送，就停下并报告根。
3. **负责人全部从主干并行开工，绝不相互堆叠，**让每个 PR 都能独立落地。
4. **swarm 验证只跑一次。** 完整 swarm 在代码就绪的 head 上跑一次。只有新行为、重新设计、或很大的新 diff，才再跑一次完整 swarm。变基、合并冲突解决、或小修，只在新 head 上配一个验证者；只改措辞的改动一个都不要。按 **swarm** 技能把独立的验证者扇出到代码就绪的 SHA 上。它们重跑检查关卡，用它配套的控制技能（比如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或一个点名的驱动器，在真实界面上实况证明承重的行为，并审计 diff。没有实况通道，或在你审计可合并报告的凭证之前，裁定都不算干净，因为没有通道会相信自己没核查过的说法。

   只有你能展示出来的问题才阻塞一个 PR：要么 head 上有一次失败的运行，要么 PR 把某行文档改错了。PR 的 base 上本来就有的问题，不管是主干带来的还是栈里下面那个 PR 带来的，都不阻塞，除非 PR 把它抄了过来或者新近碰到了它。只有用户会撞上的 bug、失败的检查关卡、或错掉的已交付文档才阻塞，其余统统放进后续处理。
5. **负责人只合并你验证过、且在它落地的那条主干上测过的东西。** 光有绿 CI 永远不构成合并授权。swarm 的通道一开跑，合并准备就变基到当前主干上、报告新 head、然后等绿 CI。

   合并前最后一刻，拉一次主干，问它的改动会不会影响这个 patch，因为主干每动一下就变基，永远没个完。当要落地的代码从没被测过时，就变基并等 CI，比如有冲突、某文件两边都改过、或有改动影响了这个 PR 跑哪些检查。两边都改过的 lockfile 不需要变基，前提是冻结安装（frozen install）在合并结果上能过、而且 PR 改动的包在那里解析出的结果和 head 上一样，因为那次安装测的正是要落地的 lockfile，安装失败就意味着必须靠变基来修好它。主干改了 patch 的某个调用方、或 patch 依赖的某个东西（比如它调的代码、或某个依赖版本）时，就在合并结果上跑 patch 的检查，过了就合并。否则就合并。如果主干会逼出合并准备之后的第三次变基，就挂起并报告根，由根来给相撞的工作排序。
6. **运行根层。** 任何放松检查关卡的东西，比如提高预算或加一条白名单，都要先有验证者的证明，再要你的一次新会签（countersign），因为负责人正是那个想要绿的人。在覆盖批准的授权下，那次会签就是批准，负责人对它的记录要指向你的会签，供通道核查。被禁用或软失败的检查一律剔出来，因为它已经守不住任何情况了。永远不要给出或绕过托管平台强制的批准，因为没有任何会签能覆盖它。

   操作者放行后，就启用 `/loop 1h` 审计，直到没有委派出去的工作剩下，因为长跑会漂移，代理会悄悄卡死。每一拍（tick）都从主干重读这本手册，修掉漂移，比如没报告的 head 或没记录的代理，办法是让它的负责人补记，因为漂移是记录里的缺口，不是卡死。它探每一个代理，一直探到叶子通道，凭副作用评判每一个，因为状态文本和摘要会藏住卡死的孩子。代理报错、开不了新一轮、或超过卡死阈值时长还没有任何新动静，就是卡死了；到了第一拍既没推送也没写轨迹行的负责人也算卡死。等你或操作者的不算卡死，去回它。立刻换掉卡死的代理，不要等它的停止落地。某一拍替操作者改动了什么，就以按 **ketchup** 技能让操作者跟上进度收尾；什么都没改的就保持安静。
7. **操作者喊停就立刻收队。** 一次挂起传到每个负责人手里，就是一条零写入的命令。每人报告自己站到哪一步，并保留自己的简报，直到操作者解除。

**回复：** 按 **ketchup** 技能让操作者跟上进度，覆盖每个 PR 的状态和裁定、合并了什么、会签及其缘由、还开着的操作者检查关卡、停着的后续事项，并附上每个 PR 和轨迹的链接。
