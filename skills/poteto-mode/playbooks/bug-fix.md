### Bug fix（修 bug）

**你拥有这个任务。计划、审查、验证。** 把调查和修复委派给子代理（subagent），自己保持主导。照子代理（Subagents）一节给每个子代理挑推理档位。

要有科学精神。每一行交付的代码都要追溯到运行时证据。"可能有用"的双保险做法是假设，不是修复。它不许交付。证据驳倒一个假设，就回退它促成的改动。证据支撑的最小改动才交付，多一行都不行。

1. 用控制技能（不可协商项（Non-negotiables）一节）在相配的界面上亲自复现，哪怕调试或插桩协议说要请用户复现。只有当控制界面确实够不到目标、并说出具体理由时才问用户，而且要先把界面开到够得着的最远处。直接复现不出来，就合成触发器、收紧条件，或加插桩直到它触发。
2. 对成因做二分搜索。列出候选假设，然后逐个排除，直到只剩一个。用受影响子系统的追踪和 **why** 技能给出的回归历史来播种假设。每一轮都选能砍掉最多剩余问题空间的分割点，拿运行时证据，排除。程序状态不明时，加插桩或日志，在代码运行时读它。不许猜。漫长或顽固的追查用 Cursor 的 `/loop` 命令驱动。在第 3 步的 `architect` 或 `interrogate` 扇出之前，用运行时证据确认幸存的*机制*。
3. 规划修复。跨函数边界就先 `architect`。把实现委派给一个子代理，用你配置的 bug-fix 模型（默认 `claude-opus-5-5-xhigh-fast`），给出具体范围。
4. 在同一个界面上验证。原始复现现在通过。"结论不明"或界面不对不算通过。要标出来。单元测试展示的是分支行为，不是 bug 不存在。
5. 暂存提交（commit），让失败的复现在 git 历史里落在修复之前。当这个 bug 有便宜的本地测试路径时，看 **tdd** 技能（skill）了解先写失败测试的节奏。测试昂贵、重集成或不明朗时跳过。
   这就是 **sequence-verifiable-units** 原则技能的典范用法，失败测试在前，修复压在上面。
6. 跑 **Opening a PR** 手册。

**回复：** 哪里坏了、根因、修复、你怎么验证的。先失败后通过的复现输出原样贴上。
