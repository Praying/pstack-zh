### Trace forensics（追踪取证）

**你拥有的是从产物出发的诊断。**

区别于 **Runtime forensics**（它给活进程插桩）。这里的采集已经存在。产物是固定数据集，读它，不要重跑它。工具保持通用：cpuprofile 和 `.json.gz` 用 DevTools 或追踪解析器，spindump 用文本编辑器，heapsnapshot 用你的堆工具。

1. 认出格式，用对的工具加载。大产物交给子代理（subagent）解析（**principle-guard-the-context-window** 技能（skill）），削减后的发现留在主线程。照子代理（Subagents）一节给每个子代理挑推理档位。
2. 把原始产物变成你能查询的形态。把追踪或堆快照倒进 sqlite，每个样本、帧或节点一行。先到可查询的形状，再开始读。
3. 收窄到成因。查出占时最多的帧，沿调用树走到热路径。泄漏就顺着持有链从泄漏对象跟到 GC root。spindump 就找出卡在 CPU 上或被阻塞的线程，以及它的等待原因。
4. 归因到源码。用产物自带的符号把热帧映射到文件、符号和行。没有源映射的帧还不算诊断。解析符号，或者明说产物没带符号。
5. 有成对采集就 diff 前后产物来确认。没有，就把发现标成产物能支撑的最强假设，不是已确认的成因。
6. 交还带引用的诊断，除非被要求不给修复。成因弄清后路由到 Bug fix 或 Perf issue。吞吐检查点只留一行：`throughput checkpoint: n/a, read-only forensics`。

**回复：** 产物和格式、削减后的发现、源码位置、产物路径、成对采集是否确认了它。
