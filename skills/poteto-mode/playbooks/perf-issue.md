### Perf issue（性能问题）

**你拥有测量叙事。计划、审查、验证数字。** 每个修复都要拴在一次测量上，不要拿读源码代替测量。

1. 用相配的控制技能抓一份基线（baseline）追踪。基线和之后的每个数字都用 **benchmark-checklist** 技能（skill）把关。
2. 追踪代码，给假设打地基。没先跑过就不要断言性能天花板。
   按顺序试性能口诀，最便宜的在前：
   1. 不要做。结果没人用的工作直接停掉，而不是把它做便宜。
   2. 做，但不要做第二次。
   3. 少做。
   4. 晚点做。
   5. 趁他们没看的时候做。
   6. 并发做。
   7. 做得便宜点。

   更靠前的口诀达到目标就停。
3. 从追踪出发规划修复。跨函数边界就先 `architect`。把实现委派给一个子代理（subagent），用你配置的 perf-issue 模型（默认 `claude-opus-5-5-xhigh-fast`）。照子代理（Subagents）一节给每个子代理挑推理档位。审查 diff。抓一份修复后的追踪。
   应用 **sequence-verifiable-units** 原则（principle）技能，每次尝试验证过再试下一次。
4. 解析并比对产物（JSON 进 sqlite，做 diff）。"结论不明"或界面不对不算通过。要标出来。
5. 在 PR 里引用测量数据。
6. 跑 **Opening a PR** 手册。

要针对某个指标做持续改进而不是一次性修复，用 Hillclimb 手册（`playbooks/hillclimb.md`）。

**回复：** 基线数字、修复后数字、差值、产物路径。
