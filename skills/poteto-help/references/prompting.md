# 给提示词措辞

提示词（prompt）写清意图和完成条件。步骤由手册（playbook）供给，所以几句大白话胜过一份规格书。

## 写进去

- 目标。说清哪里不对，或用户想要什么。
- 完成条件。要能判出通过或失败。"把它弄好"和一个时长都不算检查。
- 要出示的证据。要真实的命令输出、流程的录像、存储的值，或前后对比的数字。
- 用户已经知道的东西。一个症状、一个复现步骤、一段日志或一个链接，能替代理（agent）省掉一次搜索。
- 真实约束。"先复现"、"先别改任何代码"、"零行为变化"、"动手前先让我过目"，每一条都会改变代理的行为。

## 省掉

- 怎么做。说清要达到什么，给代理留出找更好办法的空间。
- 技能或步骤清单。手写的顺序会漏掉或打乱手册保留的步骤。只在要覆盖某一个选择时才点名技能。
- 用户对原因的猜测，等代理复述完问题再说。说出来的猜测会把搜索面收窄。

## 先加载上下文

- 报告嘈杂时，让代理先用它自己的话、用大白话把底层问题复述一遍，再做别的。误读会在任何代码出现之前现形。
- 新聊天里用 `/recall` 找回这个主题的早期工作。旧聊天里存着新代理没有的上下文。
- 动不熟悉的代码之前，用 `/how` 问机制，用 `/why` 问原因。没有追出模型的代理，会在第一个看似合理的地方修症状。
- 让 `/teach` 为某个选择摆理由，比如"说服我它修的是病因不是症状"。一套理由比一份总结好检查。

## 先设计，后计划

- 永远不要拿第一个设计。要几个选项的原型，UI 的话配截图或录像，从证据里挑。
- 让原型去回答悬而未决的问题。不要对一份抽象计划做对抗性审查，因为审查者会发明出根本不会发生的风险。
- 共享包或 API，先要 README 或一份教程，再倒推回代码。文档就成了代理自查的靶子。
- 设计定了才要计划。计划的每一步都收尾在一次检查上。

## 跟进要短

- 任务已经在聊天里之后，"做吧"、"继续"、"一直干到完成"都是完整的提示词。
- 主题变了就以"新任务"开头。否则模式会把这条消息当成上一件事的下一步。

## 走开之前

- 说"我去睡觉了"或"我走开一会儿"，代理就不再问你。
- 把完成写成每轮迭代都能跑的检查，把这个谓词交给 `/loop`。
- 要一棵从指定基点分出的新工作树（worktree）。
- 把代理会停下来问的事预先答掉，比如"提交前别问我"。
- 要一份决策日志，留待之后审计。
- 给一个出口："真卡住几个小时，就停下来写清为什么"。

## 一行改道

- 重申目标："我说过目标是复现。我还没让你修。"
- 点名原则（principle）："应用 prove it works。给我看真实输出，不是构建日志。"
- 原则名字管用，因为代理已经读过那条规则。它的回复会点名规则改变了哪个决策。
