# 把我自动化

一套引导式流程，把用户的工作惯例变成代理会遵守的技能。产出是一份为他们量身定制的 `-mode` 技能（比如 `jay-mode`、`priya-mode`）。

这个技能编排另外三个：一次内联挖掘（见第 1 步）、Cursor 内置的 `create-skill`（创作）、以及 **unslop** 技能（文字纪律）。它给它们排顺序，不取代它们。

## 流程

### 0. 检查已有技能

递归查找 `.cursor/skills/**/*-mode/SKILL.md` 和 `~/.cursor/skills/*-mode/SKILL.md` 里匹配用户称呼（handle）的。模式技能可以住在个人分类目录（`.cursor/skills/<handle>/`）里，不必只在顶层。找到了就用 `AskQuestion` 确认意图（除非他们已经说了"更新我的技能"之类）：

- 更新已有技能（重复运行时的默认）
- 重头开始（少见，先问为什么）

更新模式会改变后续流程：
- 第 1 步只挖技能上次被编辑之后的历史（`git log -1 --format=%cI <path>`）。
- 第 2 步问的是变了什么、缺什么，不是从零捕获什么。
- 第 4 步就地编辑已有文件。用户没有反驳过的小节保留。有新证据的修订。只有真正全新的规则才加新小节。

### 1. 挖掘他们的历史

扇出之前先定位当前工作区的转录。系统提示词（prompt）会指名工作区的 `agent-transcripts/` 目录。只用那个路径。不要跨 `~/.cursor/projects/*/` 去 glob。那会越过工作区边界，读到无关项目的私密聊天。

在这个范围内扫最近的代理对话，找反复出现的模式。跨历史切片并行跑多个子代理（比如最近 2-4 周，切成 3 片，保证每片材料够）。按工作给每个子代理（subagent）挑推理档位，照 **poteto-mode** 技能的子代理（Subagents）一节。每片的挖掘子代理从父级提供的、限定工作区的路径读转录，找下面这些信号，返回一份它看到的模式的简短结构化清单，附证据指针。值得搜的默认信号：

- 回复偏好（长度、语气、格式、"讲简单点"这类纠正）
- 委派习惯（子代理、模型、专门工作流、并行度）
- 验证姿态（"做完"是什么意思，单元测试对比真实复现，审查者）
- 代码与文字纪律（风格、引用的原则、lint/格式化工具）
- 流程惯例（工作树、提交、PR、审查/合并工具）
- 元偏好（任务中途修技能、提议新技能）

把信号升级之前先跨切片交叉核对。在 2 个以上切片里都见到的模式是高置信度的。孤证很弱，通常丢弃。

### 2. 直接问用户

挖掘会漏掉还没浮出水面的意图。用 `AskQuestion` 工具（结构化多选），别让用户从零手打。

形态：一到两道题，每题 4-6 个选项，类别题用 `allow_multiple: true`。先问宽的（"哪些领域最重要？"），再对选中的领域追具体选项。结构化几轮之后，用一道自由聊天题兜住选项漏掉的东西。

别一口气倒 20 道题。

### 3. 归类发现

把汇总后的信号归进小节。常见的有（只用得上的）：

- **回复风格**：长度、语气、格式。
- **自主性**：不问就做多少，MCP 工具使用。
- **先理解**：摸范围或调查改动时先用哪些技能。
- **子代理**：默认、并行度、模型对任务、专门工作流。
- **文字 / 代码纪律**：原则、lint 工具、风格指南。
- **审查与验证**：复现姿态、验证技能、实测工具。
- **流程**：git 工作树（worktree）、提交（commit）、PR、审查/合并工具。
- **技能**：技能创作习惯、先修技能、提议新技能。

**poteto-mode** 技能展示了这个形状。读它学粒度。别抄它的内容。用户的规则和 poteto-mode 的不是一回事。

### 4. 起草技能

用 Cursor 内置的 `create-skill` 技能来创作这个技能。放置规则：

- 路径：保留已有模式技能的分类。新模式在仓库已有该称呼的个人分类目录时用 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`。否则默认放项目的 `.cursor/skills/<handle>-mode/SKILL.md`（用户偏好个人技能的话放 `~/.cursor/skills/<handle>-mode/`）。
- 称呼：用户名字或自选的标识符。
- frontmatter `description`：触发条件写他们的名字 + `/<handle>-mode` + "按他们的风格干活"，不要用"写代码"或"审查 PR"这种泛关键词。
- frontmatter 格式：遵循 `create-skill` 的 YAML 规则。`description` 保持为一个 YAML 标量。需要时加引号，或用 `description: >-` 加缩进续行，以处理标点或折行。
- frontmatter 默认 `disable-model-invocation: true`。只有用户明确想让模式每轮都生效时才关掉它。

### 5. 打磨文字

把 **unslop** 技能和 `create-skill` 的写作守则用到每一行。

把草稿给用户看，收反馈。预期要改好几轮。下刀要狠。模式技能不是手册。

### 6. 落地

在从 main 分出的工作树里干活。提交并开一个 PR。不要直接往 main 推。

## 护栏

- **别过拟合到一次对话。**说过一次、另一次又自相矛盾的偏好是噪音。要见到多次实例才把它固化。
- **别耍聪明。**复述其他技能的内容、发明比喻、为代理读者写"诗意"文字，都是有成本没收益。保持可操作。
- **引用，别内联。**用户依赖的其他技能应该以路径引用出现，不是粘贴摘录。他们在别处维护的原则文档也一样。
- **小节保持最小。**只有用户在某处有具体的、非默认的规则才加小节。"沟通要清晰"不算小节。"短段落。比较选项时用表格。只有条目真正并列时才用列表。"算。
- **惯例命名用通用词。**祈使句里用"用户"或"人类"，不要用作者的名字。
- **别强求对称。**用户没有值得写下来的流程规则，就整个跳过流程小节。

## 评估

`-mode` 技能是主观产物。`create-skill` 那套测试/迭代的基准测试循环在这里没用。和用户一起做体感检查：读起来像他们吗？漏了什么吗？然后交付。

只有技能的触发准确性在实践中真成了问题，才跑描述优化循环。

## 什么时候不用

- 用户要的是任务专用技能（不是工作惯例）：只用 `create-skill`，不需要挖掘。
- 用户想固化一条窄窄的工作流（比如"我怎么写提交信息"）。那是普通技能，不是模式技能。
