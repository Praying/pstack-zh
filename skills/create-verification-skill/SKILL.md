# 创建一个验证技能

每个正经项目都需要一条脚本化的路子来驱动真实应用并证明行为：启动它、像用户那样走一遍某个功能、把证据抓下来。这个技能把它生成为一个为仓库量身定制的项目本地技能（`.cursor/skills/verify-<app>/`）。你写生成器的输出，读者是下一个代理（agent），不是人类。它会在任务中途被一个从没见过这个应用的代理冷读。

## 1. 采访仓库，而不是用户

下面这些从代码库找答案，只把观察不到的拿去问用户：

- **界面：**用户实际碰到的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用、还是库？一个仓库可以有好几个，挑出主要的那个，记下其余的。
- **运行：**应用在本地怎么启动？优先用仓库自己文档里的开发命令（包脚本、Makefile、README 快速开始）。记下端口、环境变量、种子数据、鉴权。
- **驱动：**代理怎么用程序化方式跟它打交道？先看现成的工装（harness）：Playwright/Cypress 规格、expect 脚本、PTY 辅助、能 curl 的端点、调试端口。然后才挑一份通用食谱（recipe）：Web 和 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY 工装，服务用裸 HTTP。
- **观察：**能抓到什么证据？截图、终端转录（transcript）、响应体、日志、退出码、数据库状态。
- **隔离：**两个实例能并排跑吗（端口、数据目录、配置档案）？不能的话，在生成的技能里写明：拒绝对共享实例做双重驱动，好过弄坏用户的会话。

如果检出的代码没法原样构建或启动，先修好它（或精确地报告问题）再生成。对着坏地基写出来的技能会教错步骤。当一个无关的缺失资源挡住了启动（一个 API 从不服务的静态目录、一份示例配置），生成的技能可以创建它，但要清楚标注为验证脚手架，并在清理时删掉。

## 2. 生成技能

写出 `.cursor/skills/verify-<app>/SKILL.md`，带上 YAML frontmatter（`name: verify-<app>`，以及一个 `description`，点明应用、界面、以及什么时候该用它。没有 frontmatter 这个技能就永远不会注册），再带上下面这些小节，每一节都要落在采访真正发现的东西上（不留任何占位符）：

- **启动：**启动应用做验证的确切命令，以及怎么判断它就绪了（一行日志、一个提示符）。启动必须能从空数据目录走到可用状态，包括所有迁移和种子数据。就绪的意思是可用，不只是有个进程在答应。数据库健康检查可能过了，而它的初始化脚本还在跑。也要写上拆除步骤。对于短命的 CLI 或 TUI，没有服务器要养活。启动就是构建一次二进制（或装一次依赖），然后每次驱动都在自己隔离的 PTY 或 tmux 会话里开始。
- **体检：**一项只读检查，回答"这个实例值不值得驱动？"，进程活着、版本/构建对、端口归我们、鉴权有效。一有不对劲，代理先跑它。
- **驱动：**工装食谱要用这个仓库里真实的选择器/命令，不许用示例。优先选稳定抓手（ARIA 标签、data 属性、提示符字符串、路由路径），别用坐标和 Tab 顺序。
- **证据：**为一次证明要抓什么、放到哪。写明证明标准：走真实用户路径，不走内部 setter 或只给测试用的端点；抓动作和随之而来的状态，不只是最后一屏；可视结果之外还要验证副作用（写入的文件、插入的行、发出的消息）；只在生产边界已经隔离了外部系统的地方用 mock。当安全路径是 dry-run 或测试模式时，靠观察（文件、网络、git refs）验证它实际跳过了什么，而不是信它的名字。有些 dry-run 照样碰网络或开浏览器。
- **清理：**怎么拆除这次运行创建的实例。绝不按进程名杀；只杀你启动的。清理移除实例和临时状态，绝不移除证据。证明产物要活过拆除，放在技能点名的位置。
- **辅助脚本：**技能附带的任何脚本都要可执行，调用方式要在技能正文里写出来。要读者逆向工程才能用的辅助脚本不算辅助脚本。

## 3. 播种功能地图

创建 `.cursor/skills/verify-<app>/features/README.md`，再为你能识别出的每个面向用户的功能各建一个文件（一开始瞄准前 3-5 个，从路由、命令、菜单或文档里找）。照 [`references/feature-map-example/`](references/feature-map-example/) 里的形状来，一个 README 索引加每个功能一个文件。每个文件从用户的视角回答：这个功能是什么、怎么到达它、怎么用工装驱动它、以及什么样的可观察终态能证明它有效。四个 H2 是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、和 `Gotchas`。如果种子数据缺了某条旅程需要的前置条件，这条旅程就报告失败，原因写进那个功能的 `Gotchas`。绝不为了让旅程通过而削弱它。这张地图是仓库维护中的验证来源；地图还列着别的入口时，只驱动一个顺手入口的证明是不完整的。

## 4. 交付前先证明生成的技能

把它自己的说明从头到尾跑一遍：启动、体检、驱动一个已入图的功能（一个就够；地图存在的意义就是让以后的运行去覆盖其余的）、抓证据、清理。清理之后，确认证据还存在于点名的位置。吃掉证明的清理算这一步失败。修好失败的地方，而且每次失败的迭代之后也要跑生成的清理，别让失败的尝试把进程和端口遗弃在那。从没执行过的生成技能是草稿，不是交付物。如果你是在真实目标的替身上证明的（用容器代替全新虚拟机、用本地栈代替远程栈），就把替身做过而目标不会做的每一个准备步骤列出来。这些步骤在真实目标上的运行覆盖到之前，都算未验证。

## 5. 提供维护循环（loop）

把用户指向 `/maintain-verification-skill`，在应用变化时保持这张地图诚实。只在他们问起时才建议一个节奏。
