# Notes 验证地图

本目录是验证 Notes 面向用户行为的维护中事实来源。驱动应用之前先读索引，然后拿对应的功能文件当食谱（recipe）。

## 基线（baseline）前置条件

- 在 `http://127.0.0.1:4173` 用一次性数据目录启动 Notes。
- 设好 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，让并发的运行不共享状态。
- 种入标题为 `Quarterly plan` 和 `Grocery list` 的笔记。
- 把 `control-notes` 和 `notes` CLI 放进 `PATH`。
- 跑 `control-notes doctor`，要求 URL、数据目录、构建版本号符合预期。
- 绝不驱动不是本次验证运行启动的实例。

## 驱动惯例

- 每份食谱都从基线状态开始，除非它的前置条件另有说明。
- 优先用 ARIA 角色和无障碍名称，别用 CSS 选择器或 DOM 位置。
- 把每条命令都按字面处理。带引号的名字和标志保持原样。
- 浏览器动作走 `control-notes browser`。
- 终端动作走 `control-notes cli -- <command>`。
- 改动之后恢复种子数据。清理期间不许移除证明产物。

## 证明与跳过报告

- 抓用户动作和随之而来的状态，不只是最后一屏。
- UI 证明包含一份 ARIA 快照和一张能看见应用标识的截图。
- CLI 证明包含命令、stdout、stderr、退出码。
- 改动证明包含对存储值的只读二次查看。
- 每个产物都要记下用过的功能 ID 和入口。
- 报告走不通的路径时，带上尝试过的命令和没满足的前置条件。
- 不许把跳过的入口报成经由别的路径验证过。

## 功能条目契约

每个功能文件以一个 H1 标题和一段描述用户可见行为的文字开头。然后按这个顺序恰好用四个 H2 小节。

1. `Sub-features` 列出短 ID，每个行为一行。
2. `How to get to it (user POV)` 列出每个用户入口。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，用带标签的列表项，把每个用户动作配上确切命令和可观察结果。
4. `Gotchas` 列出会浪费或弄废一次验证运行的坑。

实现细节不进地图。只点名用户路径、稳定抓手、所需状态、命令、以及可观察的证明。

## 功能

- [创建一条笔记](./create-note.md) 覆盖浏览器和 CLI 的创建、取消、持久化、清理。
- [搜索笔记](./search.md) 覆盖工具栏、键盘、CLI 的搜索，含匹配、空、清除三种状态。
