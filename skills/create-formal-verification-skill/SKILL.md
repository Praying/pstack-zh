# 创建一个形式化验证技能

测试检查的是有人想到要写的那些用例。形式化验证检查一个明说范围内的所有用例：模型里的每一种步骤顺序、界限内的每一个输入、或者每一个输入。这个技能找到仓库里这一点最要紧的部分，验证它的一条性质，并留下一个项目本地技能，让下一个代理（agent）能拿这条性质去检查一次改动。为这样的代理写它：在改动中途冷读、从没见过你的工作。用户必须能信任这个结果并据此行动，而不必去学验证语言。

## 从代码里选目标

从代码库找答案，只把观察不到的拿去问用户。用户点名了某个区域或某个 bug，就从那里开始。

好目标是代码许下的一个承诺：它一旦破了就伤害用户，而测试很少够得到弄破它的那个用例。在仓库里选这种目标里最强的那个，不是最容易验证的那个。

## 让问题来挑工具

挑能以最低成本回答这个问题的工具：模型检查器、证明助手、SMT 支撑的验证器、或其他工具。事件会不会以坏顺序发生这类问题，通常适合用模型检查器对着设计的小模型查，任何语言下 TLA+ 都是这件事的默认选择。代码本身是否对每个输入都守规矩这类问题，比如内存安全、溢出、数据结构不变量，通常适合用跑在代码上的验证器。没有验证器能跑这个语言，就直说，然后用生成的输入测真实代码，而不是手写一个函数的模型。一条必须在任何规模下都成立的性质，界限不够用时，可能需要一个证明。优先选仓库开发者装得上、跑得动的工具，并告诉用户你为什么选它。

## 怎样才算好

- **忠实于代码。** 模型或证明的每一部分都指向审查者能打开的代码。验证当成一个不可分步骤的东西，在代码里就是一个不可分步骤。名字都来自这个仓库。
- **要能失败。** 你从没见它失败过的检查什么也证明不了。让每条性质在它守护的代码的坏变体上失败一次，比如删掉一个检查、或把一个步骤换了顺序。
- **发现就保持为发现。** 当前代码破了这条性质时，用代码的语言报告它和反例。不许把性质或模型削弱到能通过为止，也不许改产品代码，除非用户要求。
- **对范围诚实。** 说清验证了什么、在什么界限和假设之下、以及漏掉了什么。一次通过覆盖的是模型或那个界限，不是整个系统。
- **离开工具也读得懂。** 性质和危害各用一句大白话说清。反例用代码的语言讲成一小串步骤。
- **重跑要便宜。** 一条命令、一个可复现的工具版本、一次短到下一个代理愿意在每个相关改动上都跑它的运行。
- **与代码步调一致。** 记下每个检查覆盖哪些文件和函数，以及你最后一次确认验证描述了它们是在哪个提交（commit）上。那个提交之后覆盖的代码变了，下一个代理就看得出验证需要再过一眼。

## 生成 verify 技能

写一个项目本地技能，frontmatter 里点明这个区域、说清什么时候该用它。没有 frontmatter，技能永远不会注册。光凭这个技能，下一个代理必须能判断一次改动碰没碰到已验证的代码、跑检查、分清真 bug 和建模错误、并在改动是有意为之的时候更新验证。把覆盖记录和同步提交放进技能里，并告诉下一个代理：只有确认了验证在新提交上依然描述这份代码，才可以把同步提交往前挪。用这个仓库里真实的命令、路径、名词，不留任何占位符。

如果检查是一个 TLA+ 模型，告诉下一个代理用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能读每一个结果。它把检查器找到的每一条不变量违反，都用大白话展示成最短路径。检查通过时，`/statechart` 会画一张系统如何在状态间迁移的图。用名字指称 `/statechart`。它的命令、选项、文件路径随版本和机器变化，所以一个都不要抄进生成的技能或其脚本里。

## 交接之前先证明它

像下一个代理那样，照着生成的技能走一遍，用一个在真实代码里弄破这条性质的临时改动。它必须抓到这个破坏。然后丢掉临时改动，确认检查回到了起点：要么通过，要么只在你要报告的发现上失败。从没跑过的 verify 技能是草稿。技能漏掉了破坏、或某一步跑不动，就修技能或验证，不要改临时改动。

## 交接

告诉用户你验证了什么、用了哪个工具以及为什么、界限是什么、检查发现了什么（大白话）、怎么跑它、以及它没覆盖什么。只有确实发现一个接近的候选时，才建议第二个目标。把用户指向 `/maintain-formal-verification-skill`，在改动没有重查验证之后把验证拉回正轨。
