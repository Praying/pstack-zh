# 把它弄明白

当任务匹配不上任何手册（playbook）时，就设计一份。写任何代码之前的交付物就是工作流本身。它是一串阶段，按任务调整严谨度，跑科学方法，留下一条人走开后回来还能审计的决策轨迹。

## 开始

开一份待办清单，第一项是阅读 **poteto-mode** 技能（skill）的原则（Principles）一节。然后把下面各阶段加为待办项。

## Phase A：框定

先摸清底细，再承诺开工。在你能说出下面三件事之前，不要开始这次运行：

- 完成的定义，写成可证伪的谓词（**prove-it-works** 原则技能）。
- 量化的范围：大致的工作单元和工作量，外加摸底暴露出的阻塞。
- 严谨度，宁高勿低。单向门和爆炸半径大的改动多给。可逆的低风险步骤少给。严谨度体现为检查关卡（gate）和产物，不是"再努力一点"。

在承诺一次长运行之前，先把框定和取舍摆出来。可逆的工作照常推进（**never-block-on-the-human** 原则技能），但一次数小时的运行要配一个检查点。

## Phase B：设计工作流

拆成原子的、可以独立落地的工作单元。排序时最危险的未知在前。脚手架和验证先于功能（**foundational-thinking** 原则技能）。

- 在动工之前搭好验证工装（harness），基线从改动前的状态采集，这样检查读出来就是"旧值对新值"。
- 对单向门的设计决策，跑 **architect** 技能（它会跑 **arena**）。形态已经明确的机械性工作跳过它。对已敲定的设计再开一场 arena 就是过度工程（**laziness-protocol** 原则技能）。
- 决定哪些东西扇出。只在接缝处并行，每个工作单元配自己的工作树（worktree）或分支（**separate-before-serializing-shared-state** 原则技能）。不要过度扇出。按任务为每个子代理（subagent）挑选推理等级，见 **poteto-mode** 技能的子代理（Subagents）一节。
- 把设计好的阶段清单写下来。人审的就是这份清单。

然后执行设计。把它的步骤作为具体条目加进待办清单，插在 Phase C 和 Phase D 条目之间。每一步都在 Phase C 的循环纪律下跑，把 Phase D 的日志织进去，每落地一步记一行，而不是把整条轨迹留到最后。

## Phase C：跑循环

每个工作单元都是一次实验。说出假设，做最小改动，在真实产物上对照谓词度量。有进展就保留，没有就回退。应用 **sequence-verifiable-units** 原则技能，验完一个单元再开始下一个，不要把检查攒到最后一起跑。

- 靠检查产物来验证，绝不信自我汇报。当某个东西通过得太轻松，先怀疑观察方法，再怀疑系统。
- 委派出去的工作配一个评审。如果工作单元钻检查关卡的空子，就重置并加固契约。如果检查关卡本身错了，在独立的改动里修它，不要绕开它。
- 裁定只有 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE 三种。INCONCLUSIVE 不算通过。不要把否定结果藏起来。

## Phase D：维护审计轨迹

用 **show-me-your-work** 技能把这次运行记成日志。figure-it-out 的工作通常规模够大，值得把轨迹提交进去，让评审在 PR 里读到。轨迹加上 diff，就是让人回来后能信任这份工作的东西。

## Phase E：验证并交回

在真实产品上（不只是工装上）对照 Phase A 的谓词检查整体。把反复出现的修正编码成检查关卡、lint 规则、检查或脚本（**encode-lessons-in-structure** 原则技能）。

**回复：** 你设计的手册、严谨度及理由、决策轨迹的路径、对照谓词验证了什么、还有什么悬而未决。
