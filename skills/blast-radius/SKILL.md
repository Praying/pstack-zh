# 爆炸半径

在改动上线前，找出它在别处弄坏了什么。用于 "blast radius of X"、"what could this break"，或者评审一个你还不信的小 diff。

是 `how` 和 `why` 的配套。`how` 告诉你代码做什么。`why` 告诉你它为什么长这样。爆炸半径告诉你它在别处弄坏了什么。

列出调用方不是这份活。代理（agent）一秒钟就能 grep 出来。这份活是 grep 给你看不到的那些破坏。

## 别信你自己的报告

听起来对的爆炸半径报告一文不值。不管真假，它读起来都一样有说服力。所以不要只交报告。找出整件事依赖的那一两个事实，用跑代码来证明它们。

### 你有几分把握

对改动安全所依赖的每个事实，只要代价不离谱，就尽量在下面这份清单里走得更深，并说明停在了哪一级。

1. 你嘴上说的。单凭这个毫无价值。
2. 你指到了那一行。真实的 `file:line`，或者库自己的源码。
3. 你证明了坏情况不会发生。你逐步走过失败路径，它到不了那里。
4. 你跑过了。一个脚本或测试，调用真实代码，你错了它就大声报错。
5. 你在跑起来的应用里复现过。

第 4 步通常就是一个小脚本，导入应用实际发布的同一个库，调用你担心的那个确切函数。

## 步骤

1. 读这个改动。看 diff、它新增、修改和删除的符号、它现在行为有什么不同，包括 diff 没写明的部分。拉取 PR 和它的提交。
2. 找出它赖以安全的那一个事实。多数看起来危险的改动，都靠单一事实保平安，比如"这个调用只丢弃已经死掉的缓存条目，别的什么都不做"。找到那个事实。它成立，大多数危险情形当场排除。时间花在这里，不要花在一长串"也许"上。
3. 看 grep 够不到的地方。读你调用的那个库的源码，检查它锁定的版本和任何本地补丁。弄清东西什么时候跑：微任务、卸载和清理、Solid 对 React。顺着符号搜索漏掉的东西走：API 返回的 JSON、某个数据库列、某种传输格式、另一种语言读同样的字节、某个功能开关、下游三跳的代码。
4. 对每个风险说实话。给它一个真实的发生概率和真实发生时的代价。保留你确认的风险。查过并排除的单独列出。引真实的 `file:line`，搜不到也是答案，绝不要编造调用方或 API。
5. 证明那个事实。写一个跑真实代码的脚本或测试，跑起来，把发生的结果贴出来。
6. 改动大或波及面广时，按 `arena` 来跑。把同一个问题问给不止一个模型，再合并答案。不同的模型能抓到不同的真实 bug。

## 交回什么

- **它做了什么。** 什么变了，包括不明显的部分。
- **它赖以安全的那一个事实。** 说出来，说明你把它推进到了哪一步，并出示证明。证不出来就写"未证明"。
- **风险。** 每条写明它怎么坏、`file:line`、可能性多大、后果多重、怎么查。要紧的那些把证明贴出来。
- **已排除。** 你查了什么，为什么没问题。
- **合并之前。** 能抓住真实 bug 的最省事的测试或复现，包括你写的脚本。

写完过一遍 `unslop`，引真实代码，发到任何公开地方之前删掉一切私密内容。

**回复：** 上面这份报告，那一个安全事实要么证出，要么标为未证明。
