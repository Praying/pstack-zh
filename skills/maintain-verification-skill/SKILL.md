# 维护一个验证技能

应用一变，功能地图就开始腐烂。这个技能是维护循环（loop），管的是 `/create-verification-skill` 生成的技能（或者任何带功能地图的项目本地验证技能）。严谨的单位是功能，不是每一句话：从源码覆盖每个功能文件、实况演练每个功能，但不必把每个列表项都跑到终态。

## 结果类别

挑一个，并说明是哪种：

- **干净（clean）：**每个功能都有源码和实况覆盖；没什么值得交付。不开分支，不开 PR。
- **有改动（changed）：**一个 PR 交付经过证明的文档、工装（harness）或地图修正。
- **受阻（blocked）：**覆盖没能完成，或者经过证明的修正没法安全交付。说清是什么挡住了它。

## 编辑范围

只编辑验证技能自己的目录（它的 SKILL.md、features/、以及它拥有的工装脚本）。运行期间绝不改产品代码。地图描述了而应用不再做的行为，要么是文档漂移（修地图），要么是产品回归（报告它，别在文档里糊弄过去）。

## 过一遍

0. **定位目标。** 找到要维护的验证技能：正文里有启动/驱动小节和功能地图的那个项目本地技能（通常是 `.cursor/skills/verify-*/`）。有好几个候选 → 问用户要哪个；一个都没有 → 停下并指向 `/create-verification-skill`，不要凭空发明目标。

1. **索引卫生。** 读功能地图的 README，glob 出它的兄弟文件。修掉缺失的、多余的、重复的、死掉的条目。轻量处理；不要生成清单。

2. **源码波。** 每个功能文件一个只读子代理（subagent），并发启动。每个都从源码解释"这个面向用户的功能是怎么工作的？"，带引用标出疑似文档漂移，并返回一份简明的实况验证食谱（recipe）。子代理绝不驱动应用、绝不编辑文件。返回形状：功能概要 / 源码入口 / 疑似漂移或无 / 一份食谱。

3. **对账。** 每个功能文件都有一份返回的概要。把重叠的食谱合并到尽量少的应用状态上。抽查引用的漂移；不要重新证明干净的说法。清扫（sweep）近期的改动，找地图里缺失的面向用户界面。判定某个缺失之前，先要一个具体的源码路径。

4. **实况过一遍。** 就算源码看起来干净也必须做。驱动全部归协调者所有，照验证技能自己的启动模型走：服务器和 UI 用一个长寿命实例串行驱动，短命 CLI 每次驱动用全新的隔离会话（由该技能的启动（Launch）一节决定，不是这一节）。每个功能至少演练一次，全程守住三条不变量，无论发生什么失败：（1）从它上次干过可疑的事以来没做过健康检查的实例，绝不驱动。首次驱动前体检，会话是单位时每个新会话体检，任何失败的驱动后再体检。体检看不到失败时（健康进程上卡住的 UI 状态），重置到已知状态或重启，别心存侥幸。（2）到目前为止抓到的证据必须活过每一次清理，在点名的位置核查过，而不是想当然。（3）一次驱动启动的任何东西都不得活得比这次驱动的用处更久。失败迭代的残留必须清理，无论会话是卡死、退出、还是共享的（共享实例只清残留，不拆实例）。技能漂移造成的体检失败就是漂移。在编辑范围内修掉并重试一次（只重启修复作废掉的部分，多一点都不做），然后才把这一遍判为 `blocked`。到不了的功能，只有给出具体前置条件（鉴权、权益、操作系统、外部状态）和尝试过的路线，才算 `verified-unreachable`。地图漏了这个前置条件，那就是漂移。分诊出的任何工装修复，交付前都要重新实况驱动。最终拆除发生在本次运行最后一次驱动之后，包括那些复证，这样没有任何东西活得比这次运行久（证据保留，按技能所说）。

5. **分诊。** 用户视角的描述错了或缺失 → 文档漂移，修掉它。能用的行为工装驱动不了 → 工装缺口，修掉它。工装修复沿用生成时的辅助脚本规则（脚本可执行，调用方式写在技能正文里）。应用行为真的坏了 → 产品缺口；为用户记录下来，别放进这个 PR。

6. **交付或停。** 有改动的：一个 PR 装经过证明的修正，先把每个改动的文件重读一遍。干净或受阻的：不开 PR，如实报告结果和覆盖情况。

在临时位置记下简明的运行笔记（覆盖了哪些功能、到不了的前置条件、确认的漂移、结果），不要提交它们。
