# 验证已有修复

当开着的 PR 或已合并的提交看起来能修掉这份报告时，用这个模式。

已有的产物（artifact）拥有修复所有权。去验证它。不要改它，不要写竞争性补丁，也不要另开 PR。

## 判定产物是否够格

要求有一件具体的产物：

- 一个开着的 PR，带针对该症状的代码改动
- 一个已合并的 PR
- 一个代码和意图都对得上的已合并提交

线程里的说法、追踪系统状态、分支名或成因假设，没有 PR 或提交支撑就不够。

有多件产物时，选源线程或追踪系统链接的那件。否则选与受影响代码最接近的，并说明理由。

## 保护工作树

仓库支持时用隔离的工作树（worktree）或另一个干净检出。不要覆盖用户的改动。

记录：

- 基线（baseline）版本
- 打补丁的版本
- PR 或提交的 URL
- 两次运行共用的构建和环境输入

使用常规的 `github.com` PR 链接。

## 测量基线

对开着的 PR，用它的基础分支做基线。

对已合并的修复，用修复前紧邻的那个版本，前提是它能构建且代表旧行为。

通过配置的控制适配器（control adapter）：

1. 拉起基线应用。
2. 确认应用和环境正确。
3. 用真实 UI 操作走报告里的路径。
4. 观察有区分度的症状。
5. 重置并重复一次。
6. 捕捉基线的录屏、截图和状态检查。

症状在基线上没出现两次，就没有基线。不要宣称修复有效。

## 测量打补丁的构建

用同样的环境和数据构建并运行该 PR 或修复提交。

1. 走同一条 UI 路径。
2. 重复两次。
3. 确认出错状态已消失。
4. 确认期望状态出现。
5. 捕捉"之后"的录屏、截图和同一项状态检查。

不要停在编译或测试上。"之后"的结果必须来自跑起来的打过补丁的应用。

## 结果

### 确认

基线复现两次，打补丁的构建消除两次。

- 运维状态标为已验证。
- 附上产物链接。
- 做完源预检（preflight）后，发一条简明的源线程回复。
- 带上前后结果。
- 不开 PR。

### 修复不足

症状在基线和打补丁的构建上都出现。

- 运维状态标为已复现但未修复。
- 附上产物链接，并说明它没有消掉症状。
- 如果本次运行还没用过常规的确认复现源更新，就发一条。
- 不开竞争性 PR。

### 无法判定

基线复现不出来、打补丁的应用跑不起来，或证据没显示有区分度的状态。

- 不要宣称成功。
- 说明哪一半测不了。
- 结果留在运维线程或运行输出里。
- 源线程里什么都不发，除非有直接提问需要回答。

## 清理

停掉两套构建，按留存政策清掉临时配置档案和截图录屏，把仓库恢复原状，不丢弃用户的工作。
