# 复现并修复问题

在源线程里等待可信的分诊标记（triage marker）。通过目标应用的真实 UI 复现确切症状。有已有修复就先验证它。只有复现确认之后才尝试一次有边界的修复。

加载自动化提供的外部 Benny 配置。配置、必需的操作、控制适配器（control adapter）或填完的功能地图（feature map）任何一项缺失，就失效关闭（fail closed）。

## 硬性安全规则

- 动手之前先冻结源频道和根线程坐标。
- 绝不在源频道发根消息（root message）。
- 每次往源线程发帖之前都先对源父消息做预检（preflight）。
- 协调者是唯一的 Slack 发帖者。
- 被委派的分析工作单元（worker）只读，只返回发现或媒体观察。
- 修复阶段的代码工作单元只有在它的环境可证明地排除了 Slack 凭据和一切 Slack 写操作时才允许编辑。否则由协调者编辑。
- 每份子代理（subagent）的提示词（prompt）都必须明确禁止 `SendSlackMessage`、`PostToSlack`、`chat.postMessage`，以及其他一切 Slack 写操作。
- 绝不给子代理 Slack 令牌、发帖指令、用于发帖的源坐标，或对外报告的许可。
- 如果子代理运行离不开 Slack 写权限，就不要启动它。
- 工具型机器人是证据来源。除非有人明确把修复委派给它们，否则它们不拥有修复所有权。
- 那个有区分度的确切症状必须通过真实 UI 交互出现两次。
- 状态检查可以确认观察结果。它绝不能注入或强行制造症状。
- 没有确认的复现，就没有动手写的修复。
- 已有的 PR 或提交会把本次运行切换到验证模式。不要另写改动盖过它们。
- 使用 `github.com` 的 PR 链接。
- 截图、录屏、日志和令牌都不要进版本控制。
- 委派分析时使用 pstack 的 `principle-guard-the-context-window`。
- 在复现、修复和验证全程应用 pstack 的 `principle-sequence-verifiable-units`、`principle-fix-root-causes` 和 `principle-prove-it-works`。

## 1. 冻结源坐标

在列工作清单或委派之前：

1. 要求触发频道等于配置的源频道。
2. 有 `trigger.thread_ts` 时把 `SOURCE_THREAD_TS` 设为它。否则用 `trigger.ts`。
3. 要求 `SOURCE_THREAD_TS` 非空。
4. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存为不可变值。
5. 读取源线程，验证它的根消息就是这些坐标。
6. 取回源永久链接。

绝不拿回复时间戳、运维（operations）时间戳或状态消息时间戳替换这些值。

每次往源频道发帖之前：

1. 按不可变坐标读取线程。
2. 确认父消息存在、未被删除，并且仍属于源频道。
3. 只用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 发送。
4. 再读一次线程，验证新消息是一条回复。

任何一项检查失败就什么都不发。绝不改到根消息重试，也不换到备用频道。

## 2. 等待分诊契约

按配置的裁定预算监视源线程。等待期间保持沉默。

只有满足以下条件才接受裁定：

- 作者与 `slack.triage_identity_user_id` 匹配。
- 它是 `SOURCE_THREAD_TS` 下的回复。
- 它包含且只包含一个配置的标记。

公开的标记形式：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只有 `bug` 或 `performance` 才继续。记下可选的追踪系统 URL。遇到 `other`、裁定缺失、作者不可信、标记冲突或超时，就静默停止。

这套标记取代了私有机器人身份和自由文本的裁定匹配。

## 3. 应用所有权与修复产物的检查关卡（gate）

动手前立刻重读线程。

### 有人明确接手修复

当有人明确认领修复、给出具体实现方案，或要求另一个代理（agent）去实现、打补丁、修复或开 PR 时，停下。

以下情况不算拥有修复所有权：

- 机器人总结证据。
- 工具查日志或工单。
- 有人让机器人诊断、解释、检查或复现。
- 机器人发了成因假设，但没答应去实现修复。

看被要求的动作来判断，而不是看有没有机器人参与。

### 已存在修复产物

如果有开着的 PR 或已合并的提交看起来能修掉这份报告，就切换到 `references/verify-existing-fix.md`。

产物可以来自线程、追踪系统的工单、仓库历史或 PR 搜索。没有提交或 PR 支撑的说法不算修复产物。

如果有人接手了这项工作但还没产出产物，就停下。不要和他们抢。

## 4. 开一个可选的运维线程

如果配置了 `slack.operations_channel_id`，协调者可以在那里发一条根状态消息。这是复现流程里唯一允许的根帖。

把它的坐标存为 `OPERATIONS_CHANNEL_ID` 和 `OPERATIONS_THREAD_TS`。绝不要和源坐标混淆。

使用配置的纯 Unicode 状态字符串。状态文字要短：

- 复现中
- 无法复现
- 受阻
- 已复现
- 验证已有修复
- 尝试有边界的修复
- 草稿 PR 已开
- 修复未落地

优先用配置好的 Cursor Slack action。只有当用户为某个狭窄的缺失能力（比如编辑这一条状态消息）配置了 `BENNY_SLACK_BOT_TOKEN` 时才用它。绝不把令牌暴露给工作单元。

如果没配置运维频道，详细状态就留在自动化运行输出里。不要拿源频道的根消息代替。

## 5. 加载并检查控制适配器

读 `references/control-adapter.md` 和 `control.feature_map_path` 处填完的映射，然后调用 `control.skill_name` 指定的技能（skill）。

找到与报告的用户路径匹配的功能地图小节。驱动应用之前先读它。如果没有小节覆盖这个功能，就把本次运行标记为受阻，不要编造路径或选择器。

要求七项能力齐备：

1. 拉起配置的目标应用和测试环境。
2. 导航到映射的功能，遍历它文档中记载的状态。
3. 用点击、输入、按键、滚动、拖拽、缩放或导航来驱动真实 UI。
4. 检查状态但不改动它。
5. 截屏。
6. 开始和停止录屏。
7. 清理进程、会话、配置档案和临时数据。

适配器缺失或任何必需能力不具备，就把运维状态标为受阻并停止。不要把截图、单元测试、状态改动或读源码冒充成 UI 复现。

## 6. 研读报告

读完整的源线程，有追踪系统工单也一并读。

收集：

- 确切的操作路径
- 期望行为
- 观察到的行为
- 两者分岔处的区分性状态
- 出现频率
- 版本、环境和平台
- 附件和错误特征
- 候选代码区域

查看截图和视频。必要时用只读的并行工作单元处理代码历史、测试思路、影响范围（blast radius）映射和媒体审查。每个工作单元只拿一个狭窄的问题，外加 Slack 写禁令。

在仓库里追溯这个操作。用 pstack 的 `why` 技能查回归历史和防御性代码。形成相互竞争的成因假设，并找出能把它们区分开的证据。

## 7. 复现

通过控制适配器拉起目标应用。

动手之前确认应用、工作区、账号、数据集和功能状态都正确。用稳定的应用标记。不要只靠窗口顺序或眼熟的标题。

用真实 UI 操作走报告里的路径。

在宣称复现之前：

1. 说清正确的最终状态。
2. 说清出错的最终状态。
3. 走到两者分岔的位置。
4. 观察出错状态。
5. 重置足够的状态，让第二次尝试独立于第一次。
6. 走同一条路径，再次观察到同一个出错状态。
7. 尽可能交叉核对一个真实状态值。

预期内的对话框、加载状态或设置步骤不是缺陷。要捕捉的是区分正确与出错行为的最终状态。

用配置的复现预算。症状在预算内复现不出来，就干脆地报 `Could not reproduce` 结果。环境提供不了必需能力，就报 `Blocked` 并说明缺了什么。

## 8. 捕捉并审查证据

复现成功时：

- 录下走到症状的完整路径。
- 截下出错最终状态的屏。
- 存一份简短记录，写明确切步骤和观察到的状态。
- 产物放在配置的临时产物目录里。

让一个只读的媒体审查者回答一个问题：证据是否直观地显示了那个有区分度的出错状态？

答案是否定或不确定，复现就不算确认。补更好的证据，或者用 `Could not reproduce`。

详细证据只在配置了运维线程时发到那里。源线程的更新保持简明。

## 9. 报告复现结果

先更新运维状态。

`Could not reproduce` 或 `Blocked` 时，源线程里什么都不发。结果由运维线程或运行输出承载。

复现确认后，跑源预检，最多发一条未经询问的源回复：

- 说明问题已复现。
- 有运维证据线程就附上链接。
- 最多带三条简短发现。
- 有追踪系统工单就附上链接。
- 默认不要 @ 负责人。

只有当配置的 Slack action 能把证据留在同一个源线程内、并且组织的留存政策允许时，才附上证据。

等配置的驳回窗口。如果有人指出设置或解读有误，就把复现纠正一次。窗口关闭且没有有效驳回之前，不进入修复阶段。

## 10. 验证已有修复

存在修复产物时，遵循 `references/verify-existing-fix.md`。

验证必须在基线（baseline）上展示症状，在打过补丁的构建上展示症状消失。两条路径都用真实 UI 走两次。

不要改动已有修复，不要加竞争性补丁，也不要开替代 PR。

## 11. 判定有边界的修复是否够格

只有以下条件全部成立才尝试修复：

- 结果是干净的确认复现。
- 媒体审查确认了出错最终状态。
- 没有出现已有的修复产物。
- 驳回窗口内没有人认领修复。
- 运行时证据锁定了根因。
- 预计的改动在配置的修复预算和仓库范围内。
- 控制适配器能跑基线和打补丁的两套构建。

任何一条不成立，就保留复现报告并停止，不开 PR。

关卡通过后，把运维状态更新为 `Attempting bounded fix`。

## 12. 定位根因并实现

协调者负责每一条 Slack 发帖、最终 diff 审查、提交和 PR。

只读工作单元可以：

- 追溯代码和历史
- 提出测试
- 映射影响范围
- 审查 diff
- 审查媒体

它们不做编辑，不执行外部写操作，不发状态，也不拥有修复。

本阶段只有当工具隔离（tool isolation）能从该工作单元移除 Slack 凭据和一切 Slack 写操作时，才允许委派一个范围收得很紧的代码编辑。它的提示词仍要带上明确的 Slack 写禁令。协调者审查这个编辑，并跑或验证必需的测试。工具隔离不确定，编辑就留在协调者手里。

用运行时证据确认机制。动手之前先排除竞争性假设。

用说得过去的最小改动修根因。

- 有便宜的本地测试目标时，调用 pstack 的 `tdd` 技能，先写失败的测试再修。
- 路径昂贵、不清晰或重度依赖集成而跳过 TDD 时，说明原因。
- 无关清理不要夹带。
- 改动超出配置的投入或风险预算就停。

## 13. 证明修复

保留原始基线证据。

在打补丁的构建上：

1. 走同一条真实 UI 路径。
2. 重复两次。
3. 展示出错状态已消失。
4. 展示期望状态取而代之。
5. 捕捉"之后"的录屏和截图。
6. 交叉核对与基线相同的真实状态值。

编译通过、单元测试、代码审查或看着合理的 diff 都不算"之后"证据。

先跑聚焦测试，再对改动行为周边的影响范围做冒烟测试。覆盖改动可能影响到的邻近状态、输入、权限、平台和失败路径。回归还在就停止，不开 PR。

## 14. 开草稿 PR

只有前后对比证据成立后才做：

- 审查最终 diff，排查无关改动和密钥。
- 跑仓库要求的检查。
- 仓库工作流允许时，拆成小而有序的提交。
- 开草稿 PR。绝不从这个流程合并或部署。
- 用追踪系统支持的 PR 语法链接配置的工单。
- 使用配置的公开 URL 形式，通常是 `https://github.com/{owner}/{repo}/pull/{number}`。
- 写清复现步骤、根因、测试结果、前后证据和影响范围检查。
- PR 文案和所有 Slack 更新都要过一遍 pstack 的 `unslop` 技能。

PR 创建失败就不要宣称成功。把提交或分支状态留在运行输出里，运维状态标为 `Fix did not land`。

成功后把运维状态标为 `Draft pull request opened`，在运维线程发一条简明回复，带上 PR 链接。不要发第二条源频道根消息，也不要再发未经询问的源回复。

## 15. 后续与清理

在配置的后续窗口内监视运维线程。

- 用已收集的证据回答直接提问。
- 如果反馈推翻了设置，做一次具体纠正并重跑一次复现。
- 不介入人类的协调和闲聊。
- 被要求停止就停。

始终调用控制适配器的清理能力。产物只在配置的留存政策允许期内保留。
