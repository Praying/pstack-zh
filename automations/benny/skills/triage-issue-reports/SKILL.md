# 给问题报告做分诊

给一条 Slack 报告分类，在它的源线程里发一条有用的裁定（verdict）。只为清楚的新缺陷（bug）建追踪单。不要在这里复现或修复。

加载自动化提供的外部 Benny 配置。配置缺失、格式错误或不完整，就停，不发帖也不写追踪系统。

## 硬性安全规则

- 源频道和根线程坐标不可变。
- 绝不在源频道发根消息。
- 绝不发到别的频道、广播回复、发私信，或另起替代线程。
- 任何追踪系统写操作之前，以及裁定发出之前那一刻，都要对源父消息做预检（preflight）。
- 父消息缺失、被删、不可访问或不确定，就停，什么都不写。
- 只发一条有实义的裁定。不要播报进度。
- 协调者（coordinator）是唯一的 Slack 发帖人。
- 委派出去的工作单元（worker）只返回发现。它们必须只读，拿不到任何 Slack 凭据或写动作。
- 每份子提示词（prompt）都必须禁掉 `SendSlackMessage`、`PostToSlack`、`chat.postMessage` 和所有其他 Slack 写操作。
- 工作单元的隔离强制不了这些限制，就在协调者里自己做。
- 绝不建无法链回源线程的单。
- 宁可不建单，也不要猜出来的或重复的单。
- 对源坐标应用 pstack 的 `principle-separate-before-serializing-shared-state`。
- 对最终裁定应用 pstack 的 `principle-minimize-reader-load` 和 `unslop` 技能（skill）。

## 1. 冻结源坐标

列工作清单或委派之前：

1. 从触发器读 `source_channel_id`。
2. 要求它等于配置的源频道。
3. `trigger.thread_ts` 存在时把 `SOURCE_THREAD_TS` 设成它。否则用 `trigger.ts`。
4. 要求 `SOURCE_THREAD_TS` 非空。
5. 把 `SOURCE_CHANNEL_ID` 和 `SOURCE_THREAD_TS` 存成不可变的值。
6. 读线程，确认它的根就是这组坐标。
7. 取一个稳定的源永久链接。

之后每次读源、往源发帖都必须用这些存下来的值。绝不用回复时间戳或运维线程时间戳替换它们。

## 2. 读完整份报告

做决定前把根消息和现有回复都读完。

抓取：

- 报告者的原话
- 有的话带上产品版本、应用构建、环境和平台
- 期望行为
- 观察到的行为
- 频率和触发条件
- 错误文本或堆栈特征
- 已有问题、提交或 PR 的链接
- 任何明确说有人已经在修的声明

检查每个相关附件。

- 截图按有用的最大分辨率看。
- 看录屏里那个把正常行为和坏行为分开的状态转变。
- 从日志、trace 和崩溃文本里读具体特征。
- 媒体需要专家看的话，用只读的媒体工作单元，问一个窄问题。工作单元只返回发现。
- 附件读不了就在裁定里说清楚。不要编造它拍了什么。

先用线程里已有的证据，再向报告者要更多。

## 3. 路由之前先追成因

选负责人或去向之前，先做一轮有界的代码和历史排查。沿路径从报告的动作追到观察到的结果。报告像回归（regression）或碰到防御性代码时，用 pstack 的 `why` 技能。

1. 找出从报告的动作到观察到的结果之间最可能的代码路径。
2. 查看可见症状属于这条代码路径还是它下面的依赖。
3. 报告像回归就查最近的改动。
4. 查有没有已合并的提交或开着的 PR 已经在处理同样的症状。
5. 把确认的事实和假设分开。

这轮排查不需要完整的根因。它必须足够扎实，避免把可见症状路由给错误的负责人。

仓库读不了就不要猜代码负责人。用保守的分类继续，并说明成因追查做不了。

## 4. 分类

选一个类别。

### 缺陷

某处违反了预期行为。例子包括错误输出、状态损坏、报错、崩溃、卡死、静默无操作，或回归。

### 性能

报告描述了可测量的慢、内存占用过高、耗电、掉帧，或其他资源问题。按缺陷对待，但保留测量数据和性能剖析。

### 功能请求

当前行为看起来是有意设计的，报告者想要另一种行为或交互能力。

### 问题或反馈

报告问的是某功能怎么用、表达了没有具体缺陷的偏好，或给了笼统的反馈。

### 改派

成因追查显示这单归另一个配置的去向管。

缺陷和功能请求的界线不清楚时，不要建单。那条唯一的裁定可以问一个聚焦的问题，并用 `other` 标记。

## 5. 应用配置的路由

从 `routing.map_path` 读可选的路由地图。

- 按确认的产品领域、代码路径或错误特征匹配。
- 成因追查指向别处时，光有可见症状不够。
- 没有路由匹配就说负责人不明。不要猜。
- 不要跨频道发帖。在源线程里告诉报告者该去哪里提这单。

给负责人发提醒默认关着。只有下面全部成立才允许提醒：

1. 路由地图明确指名了负责人。
2. 配置允许那类提醒。
3. 这条是需要负责人表态的功能请求，或最近历史以强证据指认了很可能的回归作者。
4. 负责人不是宽泛的值班组。

其他情况一律不提醒。

## 6. 用问题追踪适配器

追踪系统是一个适配器，不是硬性要求的厂商。Linear 适配器就是一个合格的例子。GitHub Issues 适配器或别的追踪系统可以实现同一份契约。

配置的适配器必须提供：

- 按文本、状态、标签、源 URL 和日期范围搜单
- 读一条单和它的链接
- 建一条带标题、正文、状态、标签和源 URL 的单
- 更新已有单时不覆盖无关字段
- 加源链接和复发记录
- Slack 交接失败时，取消、关闭或删除本次运行建的单

必需的操作不可用，那次写操作就按失败关闭处理。

配置的团队、项目、状态和标签在运行时解析。不要编 ID、建标签、指派负责人或设优先级，除非配置明确要求。

## 7. 查重

永远先查这条源永久链接是不是已经链到某条追踪单或之前的分诊（triage）回复。是的话，不要发帖也不要建重复的单。

对缺陷和性能报告，用下面这些搜追踪系统：

- 准确的错误或崩溃特征
- 产品领域
- 触发条件
- 症状
- 版本或日期窗口
- 疑似回归提交
- 源永久链接

选一个结论：

- 确定重复：特征相同，或领域、触发条件、症状都相同，或确认共享同一成因。
- 可能相关：共享成因说得通但没证实。
- 相似度弱：只是表面像。
- 无匹配。

确定重复就把源永久链接和一句简短的复发记录更新到已有单上。不要重开、改标签或改指派，除非配置这么要求。

可能相关的，在裁定里以不确定的口吻链上它，什么都不建。

关了很久的单是回归线索，不自动算还开着的重复单。

## 8. 决定要不要建单

只有下面全部成立才建：

1. 分类是缺陷或性能。
2. 行为明确坏掉。
3. 问题还开着，或没听说已修复。
4. 查重没找到确定的或可信的还开着的匹配。
5. 源父消息和永久链接过了预检。
6. 追踪系统的目标字段解析成功。
7. 裁定发不出去时适配器能做补偿。

功能请求、问题、反馈、改派、可能重复、确定重复或已修复的问题，一律不建。

新单必须自足：

- 朴素的标题，写明领域和症状
- 报告者原话引用
- 期望行为和观察到的行为
- 版本和环境，或 `unknown`
- 触发条件和频率
- 源线程永久链接
- 简短的成因追查发现，假设都标注成假设
- 支持的话内嵌截图或有代表性的视频帧
- 剩余产物（artifact）的链接
- 配置的接收状态和标签

标题里不要放猜的根因。

## 9. 发一条裁定

重新跑一次源父消息预检。然后用 `channel=SOURCE_CHANNEL_ID` 和 `thread_ts=SOURCE_THREAD_TS` 只发一条回复。

`thread_ts` 为空时绝不要调用源频道的发帖动作。

回复保持简短：

- 结论放最前面。
- 有已有单或新单就链上。
- 需要时提一句改派或一个缺失的事实。
- 最多带一个允许的负责人提醒。
- 以且仅以一行标记收尾。

标记契约：

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

只用配置的标记字符串。复现自动化只信来自这条源线程里配置的分诊身份的标记。

发完后读同一条源线程，确认裁定出现在 `SOURCE_THREAD_TS` 下面。没出现就绝不要在根上重试。

本次运行建了追踪单而裁定没落地，就用适配器的补偿动作。确认单被取消、关闭或删除。补偿验证不了，就把失败只报在自动化运行输出里。

## 10. 盯一个跟进窗口

在配置的跟进窗口内盯源线程，到点就停。

- 只回答直接问分诊身份的问题。
- 安全时把具体的更正落到追踪单上。
- 同一次运行不要发第二个标记。
- 不要掺和人的协调和闲聊。
- 有人让自动化停就提前停。

窗口最多延长一次。新的报告应该开新的运行。
